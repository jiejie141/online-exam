# online-exam 面试讲述指南

> 写这份文档的目的：让你讲的每一句话，都扛得住追问到底。
> 所有数字都回代码/真实运行核过（本机连真 MySQL 验过）。

---

## 零、40 秒版本（开场必背）

> 「这是一个在线考试与自动判分系统。核心要解决三件事：判分算错、
> 并发下重复交卷、以及缓存拿不到题。技术栈是 Spring Boot + MyBatis-Plus +
> Redis + RabbitMQ + WebSocket。
>
> 我做的几个关键决策：第一，判分写成**纯函数**，因为判分算错是这类系统
> 最不可接受的 bug，而纯函数是唯一能被穷举验证的形态，它有 13 个单测钉住；
> 第二，幂等**下沉到数据库唯一索引**，不靠应用层先查后插——先查后插在并发下
> 有窗口；第三，缓存三件事（穿透、击穿、雪崩）都有实现，且 Redis 挂了会
> 降级成直接查库，不会因为缓存抖一下就考不了试。」

**这段话里每一个数字和决策都经得起追问**，下面逐条展开。

## 一、必须能讲透的四个设计点

### 1.1 判分为什么写成纯函数

**代码**：`grading/GradingRule.java`，106 行，无外部依赖。

| 题型 | 完全一致 | 漏选 | 错选 | 未作答 |
|---|---|---|---|---|
| 单选/判断 | 满分 | — | 0 | 0 |
| 多选 | 满分 | 半分，correct=false | 0 | 0 |

**两个容易讲砸的点，主动说出来是加分**：

- **漏选给半分，但 correct 仍是 false**。如果标成“对”，正确率统计会虚高。
  这是“给分”和“算对”两件事被分开的典型例子。
- **多选题顺序无关**：`TreeSet` 归一化后再比，
  “BA” 和 “A,B” 是同一个答案。
  归一化必须用 TreeSet 而不是 LinkedHashSet —— 否则归一化结果本身
  会依赖输入顺序，一旦有人把它存起来就比较就出错。

**追问预判**：

- Q：为什么是这个规则？A：对齐真实阅卷习惯，漏选给半分是常见做法。
- Q：半分怎么避免 0.5 分？A：向下取整（`fullScore / 2`），分数一律 INT 整分。
- Q：题目没配答案怎么办？A：抛 IllegalStateException，**不默认判学生错**。

### 1.2 幂等为什么交给数据库

**这是最能体现功力的一点，一定要讲清楚“为什么不先查后插”。**

| 场景 | 机制 |
|---|---|
| 一人一场只有一份答卷 | `uk_record_exam_user`，冲突后读回 |
| 一道题一份答卷只有一条作答 | `uk_answer_record_question` + ON DUPLICATE KEY UPDATE |
| 重复交卷只判一次 | `UPDATE ... WHERE status='ongoing'`，影响行数 0 说明别人先做了 |
| 重复判分不加两遍 | `UPDATE ... WHERE status='submitted'`，0 行抛错回滚 |

**核心论点**：应用层“先查一下有没有，没有再插”，在并发下有一个窗口——
两个请求同时查到“没有”，然后都插。唯一索引把这个判断交给数据库，
数据库的约束是原子的，没有窗口。

**追问预判**：

- Q：冲突了怎么办？A：`DuplicateKeyException` 后读回已有记录，返回同一份答卷。
- Q：为什么不用分布式锁？A：这是单库场景，唯一索引就是最轻的锁，
  不需要引入额外组件。真要分库分表才需要考虑分布式方案。

### 1.3 两级缓存 + 三件事 + 降级

**代码**：`cache/PaperCache.java`，19 个单测。

- **L1 Caffeine + L2 Redis**：开考瞬间几百人拉同一份卷子，L1 命中时连网络都不出。
- **穿透**：空结果也缓存，存哨兵 `__NULL__` 而不是空串（空串有歧义）。
  **L1 也要写**——只写 Redis 的话，空卷面每 30 秒还是要打一次 Redis，穿透防护只在 L2 生效。
- **击穿**：重建前 `setIfAbsent` 抢锁，只让抢到的去查库；
  释放锁用 Lua 脚本保证**只删自己的锁**。
- **雪崩**：TTL 加 ±20% 抖动；`jitteredTtl()` 写成纯函数（随机数由调用方传入）所以能单测。
- **降级**：Redis 挂了全部走查库——缓存是加速用的，不能因为它抖一下就考不了试。

**两级缓存要被追问的一定是一致性，这里必须给出确切答案而不是"很快"**：
卷面一旦发布就不可变（`PaperItem` 是只读快照），所以 L1 允许陈旧。
窗口被配置写死：L1 TTL **30 秒** ≪ L2 TTL **600 秒**，即另一实例发布新卷后，
本实例最多 30 秒仍读旧卷。`evict()` 会同时清两层，但**它只能清本实例的 L1**。

- Q：那多实例部署时怎么办？A：**这个设计的前提是卷面不可变**。
  如果哪天卷面要支持编辑，不是把 TTL 调小，而是必须改成广播失效
  （Redis Pub/Sub 或 MQ 通知各实例 `local.invalidate`）——调小只是把窗口变窄，不是消掉。
- Q：L1 为什么要设 `maximumSize`？A：不设就是只进不出的 Map，等于内存泄漏。

**实测（README 第六节，两轮各跑一次）**：

| | 缓存开启 | Redis 停掉 |
|---|---|---|
| QPS | 4773 / 4687 | 723 / 724 |
| p99 | 55 / 56 ms | 270 / 273 ms |

**一定要主动说的可复现性故事**：

> 「最早的缓存组 QPS 在 1350 / 2047 / 4678 之间乱跳，差了三倍多。
> 查下来不是代码问题，是同机上另一个容器在崩溃重启循环里吃 CPU。
> 把它停掉之后连跑两轮，稳定在 ±2% 以内。
> **所以压测前先看一眼 docker ps，有容器在 Restarting 就别测了——
> 测出来的是噪声。**」

这段话非常加分：它说明你**会怀疑自己的数字**，而不只是报一个漂亮的结果。

**再往下一层：缓存到底省掉了哪条 SQL（开 `general_log` 数出来的）**

光有 QPS 倍数还不够——"快 6 倍"回答不了"快在哪"。所以把 MySQL 的 general_log
打开，直接数每次取卷到底打了几条库（预热 300 次 + 正式发压）：

| | 请求数（含预热） | `FROM exam_record` | 卷面 `exam_question JOIN question` |
|---|---|---|---|
| 缓存开启 | 594 | 595 条（**每请求 1 条**） | **1 条**（只有重建缓存那一次） |
| 缓存降级 | 360 | 361 条（**每请求 1 条**） | 361 条（**每请求 1 条**） |

两个结论：
1. 缓存省掉的正是那条带 `options` 大字段的 JOIN——降级时它每请求一条，开了缓存基本消失。
2. **`findByExamAndUser` 那条每请求必打，而且省不掉**。它是"你有没有进过场"的判据
   （`paperForStudent` 的第一行），是权限闸门；把它推进缓存等于把卷面越权那个洞
   从缓存里重新打开一个——**加缓存不能加在权限判断前面**。

> **"缓存命中率高" ≠ "零 SQL"。** 这个区别面试里很好用：它证明你分得清
> "哪些读可以旧、哪些读必须准"，而不是把缓存当成一个万能加速按钮。

**换个环境复测：比值稳定，绝对值跟机器走**

同一套 `bench.sh` 在另一台机器上重跑（A 组连跑四次）：
QPS **1732 / 1965 / 2003 / 2009**，p50 6–15 ms，p99 395–568 ms；停 Redis 后 QPS **250**，
avg 392 ms，p99 811 ms。**A/B 仍是 8 倍左右，比值对得上，绝对值只有一半多。**

原因不在代码：那台机器上同时跑着编辑器和 agent（两个 node 进程常驻，
`loadavg` 1.1–1.7，4 GB 内存用掉 3 GB）。**吃 CPU 的东西不一定在容器里**——
这是上面那个"压测前先看 `docker ps`"的另一个版本，也是**同一条教训的第二次出现**。

所以引用这组数字的口径是："**在这台开发机上实测 X**"，而不是"这个系统能扛 X"。

### 1.4 降级链路（异步判分）

交卷只做“改状态 + 记时间”，判分丢 RabbitMQ。Broker 不可用时
`trySend` 返回 false，**当场同步判掉**——慢一点，但不会把卷子永远挂在
“已交卷未判分”。

**追问预判**：
Q：为什么不用 WebFlux？
A：交卷+判分要整体成功或整体失败，必须用 `@Transactional` 和 ThreadLocal；
WebFlux 的事件循环模型下用不了。这是选型理由，不是“跟风用 WebFlux”。

## 二、这次补的工程设施（新增，要会讲）

### 2.1 CI：四个 job 为什么拆开

**这是你回答“你怎么保证质量”的核心。**

| job | 做什么 | 为什么单独拆 |
|---|---|---|
| unit | mvn test，Java 17 + 21 | 纯 Mockito 打桩，不依赖中间件 |
| frontend | Vitest 40 条 + 真构建一次 | **页面上的逻辑有没有错**，与 JDK 版本无关 |
| e2e | 起真 MySQL/Redis/RabbitMQ 跑 e2e.sh | **SQL 到底对不对** |
| docker | 构建镜像 + 验 fail-closed + 验 jar 里有前端产物 | 容器里是否也成立 |

**为什么 frontend 不并进 unit**：unit 跑的是 Java 17 / 21 的 matrix，前端不关心 JDK，
并进去等于同一份 Vitest 白跑两遍；而且失败信号会混在一起 —— 「组件报错」和
「事务边界写错了」是两类完全不同的原因。**拆 job 的目的就是让红叉自己说出是哪一类。**

**关键论点（一定要说）**：

> 「单元测试绿了，不代表 SQL 是对的。这个项目的 SQL 用了 MySQL 专有语法
> （JSON 列、INSERT ... AS new ON DUPLICATE KEY UPDATE），
> 我没有引入 H2——**H2 跑出来的通过是假的**。
> 所以“单测绿”和“SQL 对”是两件事，必须拆成两个 job。」

### 2.2 JWT 密钥 fail-closed（你自己写的高质量改动）

原状态：application.yml 里写着一个**能直接用的默认密钥**——等于把签名密钥
连同代码提交进了版本库。原注释写着“生产要改”，但没有任何东西强制改。

现状态：留空 + `JwtUtil` 启动即校验（空/空白/短于 32 字节都拒绝启动），
报错文案直接给生成命令。6 个单测钉住。

**这段话是最好的“自己发现并修掉”故事，务必讲**：

> 「一个用默认密钥跑起来的考试系统，从外面看和正常的**一模一样**——
> 登录能登、判分能判、健康检查是 UP。它唯一的区别是任何人都能自己签一个
> role=teacher 的令牌改成绩。**这种失败不会自己暴露，所以只能靠“起不来”
> 来暴露它。**」

### 2.3 版本化迁移（Flyway）

**为什么引入**：原来只有 `schema.sql`，它用 `CREATE TABLE IF NOT EXISTS`，
从零建库够用，但**改不了已存在的表**——给某张表加一列时改 CREATE TABLE，
对已经建过表的库会被 IF NOT EXISTS 直接跳过，
于是“新库有、老库没有”这种偏差会一直存在且不会被发现。

**这种偏差是最难排查的一类 bug，说出来很加分。**

**V1 是事后基线，不是从一开始就有的**——如实说明，面试官会认可这种诚实：
V1 内容等于原 schema.sql，已存在的库被 baseline 成 1，从 V2 开始迁。

### 2.4b 一个实测才暴露出来的迁移缺陷（比 2.4 更值得讲）

**背景**：引入 Flyway 后我第一次真起服务，应用**启动直接失败**：
`ERROR 1060 Duplicate column name 'updated_at'`。

**根因**：`baseline-on-migrate` 的判断依据只有“这个库是不是空的”，
它**无法分辨库到底处于 V1 还是 V1+V2**。只要库非空就一律标成 1，然后跑 V2。
而我验证迁移时手动跑过一次 V2 —— 于是那个库被再标成 1，V2 又跑了一遍。

**为什么这个坑值得在面试里主动讲**：

- 它在**全新库上完全不会出现**，所以我上一次验证是绿的 ——
  “全新库跑通了”根本不能证明迁移是对的。
- 它只在“已有库 + 曾经手动执行过迁移”的组合下炸，
  而这**恰恰是从旧 schema.sql 迁移过来的真实场景**。
- 失败形态是**应用起不来**，不是某个查询变慢 —— 影响面完全不同。

**修法**：让迁移自身幂等（查 information_schema + PREPARE 拼 DDL），
这是唯一能同时覆盖两种库的写法。两条分支都验过（已有库跳过 / 全新库生效）。

**面试话术**：
> 「我加完迁移，在全新库上验过，绿的。但真起服务的时候挂了 ——
> 因为 baseline 只看库是不是空的，看不出库已经跑到哪一版。
> **教训：验证迁移必须在“已存在的库”上也跑一次，
> 不能只在全新库上跑。**全新库那条路径恰好绕开了所有真实风险。」
### 2.4 一个必须主动承认的判断错误

V2 原本想加 `idx_record_grading(status, score)`，理由是
“漏判发现查询 status='submitted' AND score IS NULL 会全表扫”。

**连真 MySQL EXPLAIN 之后发现判断错了**：已有索引
`idx_record_deadline(status, deadline_at)` 的前缀正好是 status，
优化器会选它（type=ref，不是 ALL）。新索引加上后从没被选中——是冗余索引。
冗余索引的代价是真实的：占空间，且让每次写多一次索引维护，
而 exam_record 是写最频繁的表之一。

**所以最终没加，只在迁移文件里留了这段记录。**

**面试话术**：
> 「我判断索引是否被使用，一开始是靠看索引名的前缀去推，推错了。
> 后来连真库 EXPLAIN 了一次才发现。结论是：**判断索引必须 EXPLAIN，
> 不能靠推断**。」

主动承认一个自己发现的错误，比多报一个优化点更可信。

### 2.5 让"判分失败"从静默变成可见（补上的一个真缺口）

**背景**：这个缺口不是崩溃，是**静默** —— 比崩溃更值得讲。

判分走 MQ，消费者**有意不把异常抛回 Broker**（抛回去会无限重投）。
代价是失败的卷子留在 `status='submitted', score IS NULL`，没人知道。

代码里原本写着"靠 `score IS NULL` 的记录数去发现漏判"，
但**那个查询根本不存在** —— 只在两处注释里。而且更麻烦的是：
消费者把 **"并发下的正常重复判分"** 和 **"真的判不了分"** 都当成
`BusinessException` 一起 `catch` 成 `warn`。

**所以当时的真实状况是**：一份永远判不了分的卷子，和一次正常的重复投递，
在日志里长得一模一样 —— 而唯一能发现前者的手段是个不存在的查询。

**怎么修的**（三条，都很小）：

1. **把两种语义分开**：新增 `AlreadyGradedException`。重复判分是
   MQ 至少一次投递 + 定时任务兜底导致的**预期行为**，不是故障 ——
   它现在静默（`debug`），而"答卷不存在""尚未交卷"是真失败，走 `error` + 计指标。
2. **补上那个查询**：`ExamRecordMapper.countUnscored()`，
   条件同时写 `status='submitted'` 和 `score IS NULL`
   （只写一个都不对：前者会漏掉"graded 但 score 为 NULL"的脏状态，
   后者会把 ongoing 的行算进来，指标永远不会为 0）。
3. **做成指标**：`GradingSweepJob` 每 30 秒刷新
   `exam_grading_unscored`（另有 `exam_grading_failed_total` 累计失败）。
   Micrometer 依赖本来就在 pom 里，没加新依赖。

**面试话术**：

> 「判分失败的发现手段，我原来只在注释里承诺了 —— 写着'靠 score 为 NULL
> 的记录数发现漏判'，但那个查询不存在。而且消费者把并发下的正常重复判分
> 和真的判不了分，当成同一种异常一起吞了。
>
> **后果不是崩溃，是静默**：一份永远判不了分的卷子，和一次正常重复投递，
> 在日志里长得一样。修的时候我没上死信队列 —— 那会让'发现'和'修复'
> 两个职责缠在一起。我只做了让问题**可见**：分异常类型、补查询、
> 出一个指标。**失败仍然不会自愈，但它不再是静默的。**」

**这里体现的判断力**（比功能本身值钱）：
- 区分了「**发现**问题」和「**修复**问题」，先做前者
- 指标要能**回落**到 0 —— 否则它变成"历史最高值"，看板一直报警人就不看了
- 扫描任务自己失败不能把调度线程搞死（否则指标静默停更，比不报还危险）

### 2.6 一次自己撞上的 Flyway 校验和错误（我改注释改坏的那次）

**背景**：补完漏判指标之后，我顺手把 `V2__grading_lookup_index.sql` 开头
一句**指向错误**的注释改准（它说"第二段关于幂等的记录见文件末尾"，
但那段不在这个文件里）。**只改了注释，一行 SQL 没动。**

再跑 e2e，应用**启动直接失败**：

```
Migration checksum mismatch for migration version 2
-> Applied to database : -1500105960
-> Resolved locally    : -1395623977
```

**根因**：Flyway 把每个已应用迁移文件的**校验和**记在 `flyway_schema_history` 里。
**改一个字符 —— 哪怕只是注释 —— 校验和就变了**，
于是"本地这份和当初应用的那份不是同一个东西"，Flyway 拒绝启动。

**为什么这个错值得记住**：
- 它防的正是**已经上过线的迁移被偷偷改掉**。注释看着无害，
  但校验和不区分注释和 SQL —— 这是设计如此，不是缺陷。
- 我改的动机是"让文档更准确"，结果让**整个服务起不来**。
  **收益（注释更准）和代价（服务不可启动）完全不成比例。**

**正确的做法**（三条，按场景选）：
1. **已应用过的迁移文件，一个字节都不要改。** 要改描述，写到别处（如本文档）。
2. 已经在别人库里应用过、必须改的话，加一个新版本迁移，别动老文件。
3. 只在**本地**库上撞到时：`flyway repair` 重算校验和，
   或者干脆 `docker compose down -v` 拿全新库 —— 我就是这么解的。

**面试话术**：
> 「我改了迁移文件里的一句注释，只改注释没动 SQL，结果应用起不来了 ——
> Flyway 校验和不区分注释和 SQL。**它防的就是已经上线的迁移被偷偷改掉，
> 所以这个行为是对的，错的是我。**
> 我当时想着'让文档更准确'，但那个收益和'服务起不来'的代价完全不成比例。
> 现在的规矩是：**已应用的迁移文件一个字节都不改**，要补说明就写到别的地方。」

### 2.7 一次系统性的代码审查：找出三处"和项目自身模式不一致"

**背景**：前面几轮都在修单个具体问题。这一轮不再东看一处，
而是把 49 个主代码文件、剩下的模块（stats / job / security / web / ws）
**挨个过了一遍**，找的是同一类东西：**这个项目自己在别处已经解决的，
某个地方却没照做。**

这类问题单看一处都不刺眼，但合起来暴露的是"没统一的判断"。
找到三处：

**① 并发建账号是"先查后插"**（`security/AuthService.createUser`）

项目在别处**全都是让数据库唯一键裁决**的：
- `ExamSessionService.start` 捕获 `DuplicateKeyException` 后重读
- `ExamRecordMapper.markSubmitted` 用 `WHERE status='ongoing'` 的条件更新
- `ExamService.addQuestions` 也是 catch `DuplicateKeyException`

**只有建账号靠"查一下有没有"。** 两个请求同时建同名用户时会一起 insert，
并发窗口漏出一个 **500**，而串行路径给的是 **400 + "用户名已存在"**——
**同一件事两种响应**。`uk_exam_user_username` 本来就在，捕获它即可。

**② 关考任务没有逐场容错**（`job/ExamCloseJob`）

`AutoSubmitJob` 和 `GradingSweepJob` 都是**逐条兜异常**的，
只有 `ExamCloseJob` 没有 try/catch。一场 `updateById` 失败会让
**for 循环整体中断**，这一轮剩下的考试全关不掉——而且日志里只看到
"抛了异常"，**看不出"少关了几场"**。

**③ 注释承诺的和实现做的不一样**（`stats/StatsService`）

注释写"补成零人的结构，免得前端拿到 avgScore=null 还要自己判空"，
但它补的只有 `total`/`passCount`，**`avgScore` 仍然是 null**。

**这里我改的是注释，不是代码**——因为不给 avg 填 0 是对的：
**没人交卷时"平均分 0"是假数据**，会显示成一个真实存在的 0 分。
正确的判断依据是 `total == 0`。所以修的是那句自相矛盾的注释。

---

**另外还改了 `StartResult`：加了 `status` 字段。**

重复进场返回的是**原来那份答卷**，它可能已经交了卷。原来没有 `status`，
调用方无法区分"该去答题还是该去看成绩"，只能看到"拿到卷子了"就渲染答题界面——
**然后学生每答一题都被 `saveAnswer` 拒掉**。卷面照样返回，因为成绩页也要看原题。

真机验证（`curl` 打真后端）：
```
1. 首次进场      -> status = ongoing
2. 重复进场      -> status = ongoing     （保持原答卷）
3. 交卷          -> status = submitted   → 判分完成
4. 交卷后再进场  -> status = graded      ← 关键，以前区分不了
```

---

**面试话术**：

> 「前面修的是具体的 bug。这一轮我换了个做法：**不找 bug，找"不一致"**——
> 这个项目自己在别处已经有的做法，某个地方却没照做。
>
> 找到一个典型的：**并发建账号是'先查后插'**。而这个项目在别处全都是
> 让数据库唯一键裁决的——进场、交卷、组卷三处都是。只有建账号靠"查一下"，
> 于是两个请求同时建同名用户会漏出一个 **500**，而串行路径给的是
> **400 + 友好提示**。同一件事两种响应。
>
> 我还写了个 **30 线程并发建同一个用户名**的验证打真后端：
> **1 个成功、29 个友好提示、0 个 500**。
>
> 第二个是关考任务没有逐场 try/catch——另外两个定时任务都有，
> 一场失败会让这一轮剩下的全被跳过，而且**日志里看不出少关了几场**。
>
> 第三处更有意思：有个注释说'补零免得前端判空'，但它补的字段不全。
> **这一处我改的是注释不是代码**——因为不给平均分填 0 是对的，
> **没人交卷时"平均分 0"是假数据**。是我的注释在说谎，不是代码有问题。
>
> **能区分"该改代码"和"该改注释"，比能改代码更重要。**」

### 2.8 推代码时撞上的一次环境问题（不是代码问题，但值得记）

### 2.9 一个只在「干净环境第一次启动」才出现的 bug

这是整个项目里**最值得讲的一段**，因为它同时具备三个好素材：
根因反直觉、本地复现不了、以及我在排查过程中一路走错。

#### 现象

推完代码，CI 第一次真的跑起来，`e2e` job 红了。日志里是：

```
Unable to obtain connection from database: Unknown database 'online_exam'
SQL State  : 42000   Error Code : 1049
```

而**本地跑同一个脚本，当时的 24 项断言全过**（现在已经有 29 项了）。

#### 根因

发生在 `scripts/e2e.sh` 等 MySQL 就绪的那一步。原来的判据是：

```bash
docker exec exam-mysql mysqladmin ping -uroot -proot --silent
```

`mysqladmin ping` **走 unix socket**。而官方 `mysql` 镜像首次启动时，
entrypoint 会先起一个**临时实例**做初始化：

```
[Entrypoint]: Initializing database files
[Entrypoint]: Database files initialized
[Entrypoint]: Starting temporary server          <- 临时实例起来了
  ready for connections. ... port: 0              <- 只监听 socket，没有 TCP
[Entrypoint]: Stopping temporary server
[Entrypoint]: MySQL init process done. Ready for start up.
  ready for connections. ... port: 3306           <- 这才是应用要连的实例
```

临时实例一活，`mysqladmin ping`（走 socket）就返回成功。脚本于是认为就绪，
继续去执行 `schema.sql`。`CREATE DATABASE online_exam` **也返回 0** ——
但那是写进临时实例的。临时实例一关，库就没了。

十几秒后应用启动，Flyway 报 `Unknown database`。
**错误信息指向数据库，而原因在于「我们问的那个 MySQL 是不是同一个」。**

#### 为什么本地永远复现不了

本地数据卷里的库早就建好了，容器**不会重新初始化**，
所以永远走不到「临时实例」那条路径上。

**这个 bug 只在第一次 `docker compose up` 的干净环境里出现。**
换句话说：它专门等着新同事入职第一天、或者 CI 第一次运行时才发作。

#### 修法

把判据换成**走 TCP** 的版本：

```bash
docker exec exam-mysql mysqladmin -h 127.0.0.1 -uroot -proot ping --silent
```

临时实例是 `port: 0`，没有 TCP，连不上；连得上就说明正式实例已经在 3306 服务 ——
**正是应用真正需要的那件事**。判据从「进程在不在」变成了「应用能不能连上」。

同时给 `schema.sql` / `seed.sql` 两条 `docker exec` 补上退出码检查：
原来不检查，而「建表悄悄失败、脚本继续往下走」正是这个问题难查的原因 ——
日志里每一步都显示正常，直到十几秒后报一句风马牛不相及的错。

修完 CI 全绿，进度里能看到 `MySQL ready after 5 checks (TCP 可查)`；
应用 `app ready after 8 checks`（16 秒），5 分钟的等待预算绰绰有余。

#### 如果被追问「你怎么发现的」——这才是真实过程

诚实讲，我在这上面花了**十四轮**，而且前十三轮没找到它。过程是这样的：

1. **前四轮**我一直在修「为什么 CI 看不到原因」：
   先是 `::error::` 发不出来（GitHub 的 `run:` 默认带 `-e`，管道那行非 0 就退出了），
   改成逐行 `::notice::`，40 行只收到 10 行。
   然后才发现 **annotation 有条数上限（约 10 条，超出静默丢弃）**，
   而且每条还有长度上限会截断。
2. **第五轮**终于发现 `e2e.sh` **一次都没跑过** ——
   workflow 里写的是 `bash scripts/e2e.sh > target/e2e-run.log 2>&1`，
   而**重定向是 shell 在启动 bash 之前处理的**；`target/` 不在仓库里（被 gitignore），
   shell 直接拒绝建立重定向，命令根本不执行，`$?` 拿到 1。
   加一句 `mkdir -p target` 就解决了。
3. **第六到十三轮**都在拿应用日志。
   每换一种方式（`grep` 截取、`tail`、artifact），就撞上另一个「信息通道本身的上限」。
4. **第十四轮**把日志 gzip+base64 切片发出来，才第一次看到真正的异常：
   `Unknown database 'online_exam'`。

#### 这段经历本身才是最该讲的部分

回头看，十四轮里只有**两轮**在修项目真正的 bug（`target/` 目录、MySQL 判据），
**其余十二轮都在修「我看不见」。**

这与本项目里另一个教训是同一个形状 ——
README 里「测量精度会被测量方法本身限制」（50 ms 轮询把延迟量化成了 50/100/150 ms）：

> **一个只能看到 exit code 的 CI，等于没有 CI。**
> **一个会把消息静默丢弃的通道，等于没有通道。**

而最尖锐的一句是：

> 我把「没看到」当成了「不存在」。
> 先是「脚本没跑」被当成「脚本跑了但出错」，
> 再是「消息被丢弃」被当成「消息没产生」，
> 最后是「库建在临时实例上」被当成「库没建起来」。
> 三次都是**先假设了证据链的最后一环是完好的**。

如果面试官问「这个 bug 你怎么定位的」，
**不要只讲 `mysqladmin ping` 那个点** —— 那个点十分钟就能讲完，
而「我怎么知道该往哪看」才是我真正想说的能力。

### 2.10 一个「HTTP 200、JSON 有数据、页面却是空的」bug

上面 2.9 是「工具看不见」，这一条是反过来的：**工具什么都看得见，只是我没看**。

**现象**：老师端「成绩统计」页，五张卡片全对（已判分人数 1、平均分 44.0），
成绩分布的柱子也出来了，唯独下面「逐题正确率」这张表：
**「作答人数」整列空白、「正确率」整列显示「—」**。

**当时最容易得出的错误结论**：「后端没返回这些人」。因为直接 `curl` 这个接口，
返回的是：

```json
{"code":0,"message":"ok","data":[
  {"questionId":2,"stem":"下列哪个集合类是线程安全的？","correctCount":0}
]}
```

HTTP 200，`code: 0`，`data` 有 10 个元素，`correctCount` 也是对的。
**一切正常 —— 除了少了 `attempt` 这个字段。**

**根因**：Mapper 里写的是

```sql
COUNT(*) AS attempt_count
```

而 DTO 字段叫 `attempt`：

```java
public class QuestionAccuracy {
    private Integer attempt;        // ← 这里是 attempt
    private Integer correctCount;
}
```

MyBatis 的 `map-underscore-to-camel-case: true` 只做一件事：
把 `snake_case` 转成 `camelCase`。所以 `attempt_count` → `attemptCount`，
然后去找 `setAttemptCount()`，**找不到也不报错**，静默跳过。
`correct_count` → `correctCount` 恰好对得上，所以那一半是好的。

> **对不上就不映射，不映射就不报错，不报错就是 null。**

**为什么一直没发现**：

- 我写 Mapper 时心里想的是「SQL 的列名」（`attempt_count` 更像 SQL），
  DTO 里写的是「Java 的字段名」（`attempt` 更像 Java），
  **两个名字在两份文件里各自都合理**，只有摆在一起才看得出错。
- 前端 `rateText()` 里写的是 `if (!row.attempt) return '—'`，
  **这个「防御」把 null 渲染成了一个看起来很正常的长横线**，
  而不是报错。我看到的不是「数据缺失」，是「一个设计好的空状态」。
- e2e 脚本 `[9] 老师端统计` 那一节，断言写的是
  `missed[0]["correctCount"] == 0` —— **它只看了对的那一半**。
  接口 200、题数 10、correctCount 全对，脚本就是绿的。

**修法**（两行）：

```sql
COUNT(*) AS attempt          -- 别名改成和 DTO 字段同名
ORDER BY ... ASC, attempt DESC
```

**真正值得讲的是补测试的思路。**
补一条 `assert attempt == 1` 只挡住这一处，下次换个字段名照样漏。
所以写的是 `MapperAliasTest`：

1. 用反射取出每个 `@Select` 注解里的 SQL 文本；
2. 正则抓出所有 `AS xxx` 别名；
3. 按 MyBatis 的规则转成驼峰；
4. 核对 DTO 上**确实声明了那个字段**。

它不连数据库、不执行 SQL，纯静态，但**覆盖所有统计 SQL** ——
以后再加一个统计查询，别名写错会直接红在 `mvn test`。
另外配了一个「确实扫到了别名而不是空跑」的正向用例
（否则哪天注解改成 XML 映射，正则扫不到东西，前面几条会**空跑通过**，
那就成了假绿灯 —— 和 2.9 的教训是同一个）。

**变异验证**：把别名改回 `attempt_count`，测试报

```
SQL 别名 attempt_count → 驼峰 attemptCount，但 QuestionAccuracy 上没有这个字段
（MyBatis 遇到对不上的别名不报错，只会把字段留成 null，表现为页面上整列空白）
```

**如果面试官问「你怎么保证 SQL 是对的」**，这条比 2.9 更好用：
2.9 讲的是「环境骗我」，这条讲的是 **「类型系统之外的字符串契约」** ——
SQL 里的列名和 Java 里的字段名之间没有任何编译期检查，
中间只有 MyBatis 一条**会静默失败的**约定。
能想到把这条约定写成测试，比多写十条断言更能说明问题。

### 2.11 「按需引入」装了插件却没摇掉：一次 41% 的体积优化

**背景**：前端主 chunk 1.11 MB（gzip 370 KB），构建时有一条 `chunks are larger
than 500 kB` 警告。这个页面只用了 17 个 Element Plus 组件，1.11 MB 显然不合理。

**第一版做法（照文档抄的，没效果）**：装 `unplugin-vue-components` +
`unplugin-auto-import`，在 vite 里配 `ElementPlusResolver()`。
重新构建 —— **体积几乎没动**。

**为什么没动**：去看 `unplugin-vue-components/dist/resolvers.js`，当 element-plus
版本 >= 1.1.0-beta.1 时，`resolveComponent` 返回的是

```js
{ name, from: 'element-plus/es', sideEffects: ['element-plus/es/components/base/style/css', ...] }
```

而 `element-plus/es/index.mjs` 是一个 **barrel**（再导出汇总文件），它第 293 行
`import defaults_default from "./defaults.mjs"`，`defaults.mjs` 里
`makeInstaller([...component_default, ...plugin_default])` —— **把所有组件都 import 了一遍**。
打包器无法证明这个模块无副作用，于是**一个组件都摇不掉**。

> 装了插件 ≠ 摇掉了。**「按需引入」这四个字最会骗人的地方就在这里：
> 配置看起来完全正确，构建也成功，警告也还在。**

**改法**：自己写 resolver，直接指向深路径。难点是**组件名不能靠 kebab-case 猜目录**：

| 导出名 | kebab-case 猜的目录 | 真实位置 |
|---|---|---|
| `ElTableColumn` | `table-column/` ❌ | 在 `table/index.mjs` 里一起导出 |
| `ElFormItem` | `form-item/` ❌ | 在 `form/` 里 |
| `ElOption` | `option/` ❌ | 在 `select/` 里 |
| `ElCheckboxGroup` | `checkbox-group/` ❌ | 在 `checkbox/` 里 |

所以做法是**扫一遍 `es/components/*/index.mjs`，把每个文件 `export { ... }` 里的
`El[A-Z]*` 名字建成一张 `Map<组件导出名, 目录名>`**，运行时查表。查不到就不接管，
让 Vue 自己报「未注册组件」而不是静默降级。

**结果（实测）**：

| | 前 | 后 |
|---|---|---|
| JS 总计 | 1,113,341 B | **657,727 B（降 41%）** |
| 主 chunk gzip | 370 KB | **230 KB** |
| CSS 总计 | 362,823 B | **148,393 B** |
| 模块数 | 1737 | 1159 |
| 500 kB 警告 | 有 | 无 |

复查新产物：`ElTransfer` / `ElCascader` / `ElCarousel` / `ElUpload` / `ElTableV2` /
`ElColorPicker` / `ElTimeline` 全部 **0 命中**；只有 `ElTree` 剩 3 处、
`ElTreeSelect` 剩 1 处 —— 那是 `select` 的依赖链带进来的，砍不掉也不该砍。

**这段为什么值得讲**：它同时展示了三件事 ——
① 会读依赖包的源码，而不是只信文档；
② 用「产物里 grep 组件名」这种方式**验证优化真的生效**（而不是看到构建成功就宣布成功）；
③ 分得清「配置写对了」和「效果发生了」。

> 面试版一句话：「按需引入配了插件但体积没变，因为我查了源码发现官方 resolver
> 在 2.x 上指向的是 barrel 文件，tree-shaking 从一开始就不可能生效。改成手写
> 深路径映射表之后，JS 从 1.11 MB 降到 657 KB，我是在产物里 grep 过组件名确认的。」

### 2.12 又一次越权：这次是"整份卷子能被任何人拿走"

**背景**：2.7 那轮修的是老师端——七个入口都补了 `created_by` 归属。
但那轮只看了"考试归谁管"，没看"卷子归谁能看"。补完之后回头再扫学生端，
发现 `GET /api/exams/{examId}/paper` 的签名是 `paper(Long examId)`：

```java
// 改之前
public List<PaperItem> paper(Long examId) {
    ... 三级缓存读卷面 ...
}
```

**它一个权限判断都没有。** 任何登录用户（哪怕是另一门课的学生）传一个
`examId` 就能把整场卷子拿走，**包括还没开考的那一场** ——
考试计划明天上午开，今天就能把十道题连分值一起看完。

**这比"看到别人的数据"严重一个量级。** 数据泄露是"某人看到了他不该看的"，
而题面提前泄露是**这场考试作废** —— 它还照样开考、照样判分、照样排名，
只是成绩已经不作数了，而且**没有任何人会发现**。

**怎么修的**：拆成两个方法。

```java
public List<PaperItem> paperForStudent(Long examId, Long userId) {
    ExamRecord record = recordMapper.findByExamAndUser(examId, userId);
    if (record == null) {
        throw new BusinessException(403, "还没有进入这场考试，不能取卷面: " + examId);
    }
    return loadPaper(examId);
}

List<PaperItem> loadPaper(Long examId) {   // 包级可见，不做权限判断
    ... 原样保留的缓存逻辑 ...
}
```

三个刻意的地方：

- **判据选"有没有自己的答卷"，不选"考试是否 published + 在时间窗内"。**
  答卷只可能在 `start()` 通过那三道校验（已发布 / 已开考 / 未结束）之后
  才被创建出来。所以"我有一份答卷"本身已经证明"我当时是合法进场的"。
  选这个判据的好处是**不用把时间窗判断再抄一遍** —— 抄一遍就多一处会写歪的地方，
  而且两处判据将来一定会漂移。
- **不区分"考试不存在"和"你没进过"。** 两种都回 403 同一条消息。
  分开回答等于免费送一个探测 `examId` 是否有效的接口 —— 这和
  `ExamAccess` 那边"用 403 不用 404"是同一个判断。
- **内部路径留一个不做权限的 `loadPaper`。** `start` / `result` / `saveAnswer`
  已经各自校验过身份了，它们走这条。**不能把权限判断下沉到读卷面那一层**，
  否则 `start()` 第一次进场时会因为"还没有答卷"而拿不到题 —— 死锁在入口。

**顺带补的第二个洞**：`ExamService.addQuestions` 只判"这场考试是你的"，
没判"这些题是你的"。题库里别人的题可以被悄悄塞进自己的卷子。
更麻烦的是**这个方法没有 `@Transactional`**，所以顺序本身是逻辑：

```java
// 先全部校验，再全部写入
List<Question> questions = new ArrayList<>();
for (Long questionId : questionIds) {
    Question q = questionMapper.selectById(questionId);
    if (q == null) throw new BusinessException("题目不存在: " + questionId);
    if (!teacherId.equals(q.getCreatedBy())) {
        throw new BusinessException(403, "不能把别人的题目加进自己的卷子: " + questionId);
    }
    questions.add(q);
}
for (Question q : questions) { ... insert ... }
```

边校验边写的话，列表中间夹着一道别人的题时，**前面几道已经落库**，
卷子成了改了一半的半成品，而调用方只看到一个 403。
这个坑有专门一条用例钉着（`列表里夹着别人的题目就一道都不写`）——
它测的不是返回值，是 `verify(examQuestionMapper, never()).insert(...)`。

**验证方式**（和前面几轮同规矩：新测试必须在坏代码上变红）：
- 把 `paperForStudent` 的校验删掉 → `PaperAccessTest` 6 条里 **3 失败 2 错误**；
- 把 `addQuestions` 的归属校验删掉 → `ExamServiceTest` **2 条失败**；
- 把"先校验后写入"改回"边校验边写" → 同样是 **2 条失败**（`列表里夹着别人的题目就一道都不写` 那条就是为它写的）。

> 面试版一句话：「补完老师端归属我回头扫学生端，发现取卷面那个接口根本不判权限，
> 任何人猜一个 id 就能把还没开考的卷子拿走。修的时候判据选的是'有没有自己的答卷'
> 而不是重抄一遍时间窗，因为答卷只可能在合法进场后才存在，这样少一处会漂移的判断。
> 另外我把内部读取和对外读取拆成两个方法，权限判断不能下沉到读卷面那层，
> 否则第一次进场会拿不到题。每条都做了变异验证 —— 把校验删掉，测试必须红。」

### 2.13 四个「不是功能」的设施：分页 / 多环境 / traceId / 停机与任务锁

这一段的价值不在「我加了四个东西」，而在**每一条都有一个非默认的选择**，
面试官追问「为什么这么写」时答得出来。

#### （1）分页：返回结构变了，就要跟着改所有消费方

老师端两个列表原来是一次 `selectList` 全量返回。改成 MyBatis-Plus 的
`PaginationInnerInterceptor` 之后返回 `{items,total,page,size}`。

三个刻意的地方：

- **`page` 从 1 开始**，传 0 或负数**夹到 1**，不返回 400。「翻页」是高频动作，
  不该成为一个新的错误来源；而且前端少写一层兜底。
- **`size` 上限 100，并且在 controller 里显式夹一遍**，不依赖插件静默改写。
  插件会把 `size=100000` 改成 100，但**返回体里的 `size` 字段仍是请求值** ——
  前端拿它算总页数就会算错。显式夹一遍之后，请求和响应是同一个数。
- **`/api/exams/available` 刻意不分页。** 它被时间窗（已发布 + 已开考 + 未结束）
  天然限制在很小的结果集里；加分页只会让前端多一层无意义的翻页，
  而且「能考什么」这个接口本来就要一次给全。

配套加了 `V3__exam_teacher_list_index.sql`：`(created_by, start_at)`。
**等值条件列放最左、排序列放右**，这样一条索引同时承担过滤和排序，避免 filesort；
**没有加 DESC 索引** —— B+ 树反向扫描的代价和正向一样，单独再建一份只是多一份写入开销。

#### （2）多环境：拆文件只解决一半，另一半是「起不来」

原来只有一份 `application.yml`，数据库口令 `root/root` 明写在文件里。
拆成 `application.yml` + `application-dev.yml` + `application-prod.yml`，
prod 里所有凭据写成 `${EXAM_DB_PASSWORD}` **不给默认值**。

**但只做到这里是不够的。** 不给默认值的效果是「连库那一刻才炸」，
而那时应用已经起了半个 —— 报错栈指向 Hikari，不指向「你忘了配口令」。
所以加了 `config/ProdConfigGuard.java`：`@Profile("prod")` + `@PostConstruct`，
启动最早期就检查三个口令（非空 / 不在示例口令集 / ≥8 字符）和 JWT 密钥
（≥32 字节 / 字符种类 ≥8），**把所有问题一次全列出来**再抛异常。

为什么要列全：只报第一个的话，改完重启又冒出下一个，一轮一轮试 ——
部署失败本来就急，不该再让人猜。这条有专门的用例（`多个问题一次性全报出来`）。

还有一条容易被忽略的：`32 个 'a'` 能过「≥32 字节」的长度检查，但那不叫密钥。
所以加了字符种类下限，并且有用例钉着（`JWT密钥是重复字符时拒绝启动`）。

#### （3）traceId：一个请求的日志要能自己认出来

没有 traceId 时，一个请求打出的几行日志和其他请求的日志交错在一起，
排查只能靠时间戳对齐 —— 并发一高就彻底不可读。

`web/TraceIdFilter.java` 是 `Ordered.HIGHEST_PRECEDENCE` 的 `OncePerRequestFilter`：
读 `X-Request-Id`，没有就生成 16 位，放进 MDC，同时写回响应头，`finally` 里 `MDC.remove`。

四个细节：

- **`finally` 里必须 `MDC.remove`。** Tomcat 的线程是复用的，不清就会串到下一个请求上，
  而这种串号**只在并发下出现**，本地单请求永远复现不了。有用例专门钉它。
- **外部传进来的 id 要校验。** 只接受字母数字和 `-_.`、长度 ≤64，否则重新生成 ——
  否则等于允许外部往日志里注入换行和伪造字段（日志注入）。
- **写回响应头。** 前端报错时能把这个 id 一起带给你，你就能直接定位到那一条请求。
- **`logback-spring.xml` 里刻意不用 `%clr()`。** ANSI 颜色码会让 `grep` 把日志文件
  判成二进制，只回一句 `Binary file matches` 而不给行号 —— 日志是为了被搜的，
  不是为了让终端好看。这是我在排查 CI 问题时实际踩到的。

#### （4）优雅停机 + 定时任务锁：锁是优化，不是正确性前提

`server.shutdown: graceful` + `spring.lifecycle.timeout-per-shutdown-phase: 30s`：
停机时先停止接新请求，等在途请求做完再退。没有它，一次滚动发布就会把正在交卷的人打断。

三个 `@Scheduled` 任务（自动收卷 / 到点关考 / 漏判扫描）在多实例下会被**每个实例各跑一遍**。
`job/JobLock.java` 用 Redis `setIfAbsent` 抢锁、Lua 脚本校验 token 后释放
（和 `PaperCache` 同一套写法，直接复用已有的 `StringRedisTemplate`，没有引 Redisson）。

**最关键的一个取舍：Redis 不可用时降级成无锁执行，而不是跳过这一轮。**

> 「锁在这里解决的是『别重复干活』，不是『别干错事』。三个任务本身都是幂等的 ——
> 自动收卷只改状态还没变的记录、关考只关已经到点的、扫描只是读。
> 所以抢不到锁跳过没问题，Redis 挂了**也必须照跑**。
> 反过来如果 Redis 一挂就停止收卷，那才是真把可用性绑在了缓存上。」

这条分支做过变异验证：把 `return task.get()` 改成 `return null`，
`JobLockTest.Redis不可用时降级为无锁执行` 立刻红。

#### 验证与未验证（要说清楚）

- 后端单测从 153 条增加到 **178 条**（新增 `JobLockTest` 7 / `TraceIdFilterTest` 8 /
  `ProdConfigGuardTest` 10），全绿；前端 40 条仍全绿；`npm run build` 通过。
- **分页与 V3 迁移没有连真库验过** —— 这台机器上 Docker Desktop 起不来，
  只做到编译级与单测级。真实 SQL 由 CI 的 e2e job 每次 push 验（`scripts/e2e.sh`）。
  **这一条要主动说，不要等被问。**

## 三、已知限制（必须主动说，别等被问）

README 第八节列了 12 条，**挑这几条主动说**，能证明你分得清“做完”和“没做”：

0. **分页与 V3 迁移没连真库验过**（本机 Docker 起不来，只做到编译 + 单测级；
   真实 SQL 由 CI 的 e2e job 每次 push 验）。**这条要先说，它是最容易被追问的。**

1. **判分失败不会自动重试**：消费者吞异常只记日志，靠 score 为 NULL 的记录数
   发现漏判。要做对需要死信队列 + 重试计数。
2. **没有防作弊**：无切屏检测、无题目乱序、无选项乱序。
3. **WebSocket 没做水平扩展**：连接存在单机内存，多实例需要换成广播。
4. **JWT 无法主动失效**：改密码或踢人需要额外黑名单。
5. **Dockerfile 没在真实镜像上构建过**（本机 Docker 代理失效拉不到镜像），
   只做到指令结构已校验；CI 的 docker job 会在能联网的 runner 上真跑。
6. **压测客户端和服务在同一台机器**，QPS 是保守值；而且**换台负载不同的机器绝对值会差一倍多**
   （另一台机器实测 ~2000 / 250，比值仍是 8 倍）。所以只能讲"这台机器上实测"，
   **不能把 4773 说成系统容量**。压测期间机器上跑着编辑器/agent 这类"不在容器里"的负载，
   也会直接压低数字。
7. **前端只有单测，没有端到端**：Vitest 40 条钉住倒计时、多选拼接、401 跳转、
   交卷弹窗和三态，但没有 Playwright，所以「后端改坏了前端照样绿」抓不到。
