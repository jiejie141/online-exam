## 零、结论先说

**四个高危数字里有三个是错的，其中「13 → 50 条评分规则」是彻底的误读。**
下面按「面试官会怎么问 → 真相 → 怎么改」逐条写。

**先说一句公道话**：这个项目的 README 写得很诚实 ——
第 207 行明说「全部来自真实运行输出，不是估算」，第 240 行起专门列了
「已知限制（没做的，不装作做了）」。**问题不在项目，在简历的转述把两件事混在了一起。**

## 一、🔴 最严重：「13 条判断完善为 50 条评分规则」

### 这个数字是怎么来的

README 第 249 行有一张测试覆盖表，其中一行是：

```
| GradingRuleTest | 13 | 单选/多选/判断的满分、漏选半分、错选… |
```

**那个 13 是「测试方法数」，不是「评分规则数」。**

而 README 第 209 行的小节标题是：

```
### 判分（bash scripts/e2e.sh，50 名学生各交一份 10 题卷）
```

**那个 50 是「参加压测的学生人数」，不是「规则条数」。**

两个互不相干的数字被拼成了「规则从 13 条完善到 50 条」，还配上了「完善」「逐条一致」
这类听起来像有变更历史的措辞。

### 真相

判分规则的全部实现在一个文件里：
`src/main/java/com/jiejie/exam/grading/GradingRule.java` ——
**整文件 106 行，一个类，四个分支**：

| 题型 | 完全一致 | 漏选 | 错选 | 未作答 |
|---|---|---|---|---|
| 单选 / 判断 | 满分 | — | 0 | 0 |
| 多选 | 满分 | 半分（correct=false） | 0 | 0 |

代码里**没有任何编号到 13 或 50 的规则清单**（grep 序号注释，零命中）。

### 面试官会怎么问

> 「你说的 50 条评分规则，能打开文件让我看看吗？」

**这一问就穿了。** 更糟的是，它会让面试官怀疑你其它数字的真实性。

### 怎么改

**不要提「规则从 13 条到 50 条」。** 改成你真正做的事：

> 「判分写成**纯函数**，因为判分算错是这类系统最不可接受的 bug，
> 而纯函数是唯一能被穷举验证的形态。多选有四条规则：全对满分、漏选半分、
> 错选零分、未作答零分；其中**漏选给半分但 correct 仍为 false** ——
> 如果标成『对』，正确率统计会虚高。这一条有 13 个单测钉住。」

**「13 个单测」是真的，「纯函数四分支」是真的，「漏选不算对」是真的。**
这么说既准确，又比那个假数字更能体现判断力。

## 二、🔴 「83 条 HTTP 与权限校验在真实运行的服务上全部通过」

### 真相

| 说法 | 实际 |
|---|---|
| 83 条校验 | `scripts/e2e_check.py` 里 **32 条** check（写这份核查时是 20 条，后来补了成绩单 3 条、别名映射 2 条、老师端互查 3 条等，并接进 CI） |
| 全部通过 | 脚本连真 MySQL / Redis / RabbitMQ 跑，**已经在 CI 里**（`.github/workflows/ci.yml` 的 `e2e` job，每次 push 都跑） |

那 32 条的内容我逐条列过，质量其实很高：错误口令 401、
**卷面 JSON 里不含 answer 字段**、别人查不到我的答卷（403）、
**漏选题的正确率算 0**、**逐题正确率的 attempt 字段不能是 null**、
批量判分分数一致（都是 87）等。
问题只是数字被夸大了将近三倍。另外「83」这个数在项目里根本不存在。

### 怎么改

> 「端到端脚本 `e2e_check.py` 里 **32 条接口与权限校验**，连真实
> MySQL / Redis / RabbitMQ 跑；包括『卷面 JSON 里不能有 answer 字段』
> 和『漏选题的正确率算 0』这类容易漏的点。
> **这个脚本已经进了 CI 的 `e2e` job，每次 push 都会在干净环境里跑一遍** ——
> 它不是「我本机验过」，是回归门禁。」

顺带说明一下我改它的过程，这比数字本身更值得讲：这个脚本**原来没进 CI**，
是我后来加进去的；而加进去之后它连着红了 14 次，
真实根因是「等 MySQL 就绪」用的是 unix socket 探测，
正好命中了官方镜像首启时的**临时实例**（详见 `INTERVIEW-PREP.md` §2.9）。
**「把这个脚本放进 CI」这件事本身，才让那个 bug 浮出来。**

## 三、🟠 三个「项目里根本不存在」的说法

### 3.1 「CI 分四类作业，覆盖 PostgreSQL 真实数据、容器化换机与备份恢复演练」

**这个项目没有 CI。连 `.github` 目录都不存在。**

这些全部是**另一个项目（lab-booking-agent）**的事实，被搬到了这一栏。
（lab-booking 确实有 4 个 CI job，其中一个跑真 PostgreSQL —— 但那是 Python 项目。）

### 3.2 「一次请求可串联起来」的 request_id

**本项目没有 request_id 机制**（grep 零命中）。同样是 lab-booking 的特性。

### 3.3 「三个健康检查接口」

`/actuator/health` 与 `/actuator/info` 是 **Spring Boot Actuator 框架自带**的，
在 `SecurityConfig.java:38` 被放行匿名访问。
**「我写了三个健康检查接口」不成立** —— 那是配置放行，不是实现。

### 怎么改

这三条**整条删除**，或如实写成：

> 「Spring Boot Actuator 暴露健康检查，放行匿名访问便于探活。」

**千万不要留着。** 面试官只要问一句「你的 CI 配置文件在哪」，
你就得当场打开一个不存在的目录。

## 四、🟠 「6 个数据库迁移脚本」

没有 Flyway / Liquibase，没有版本化迁移脚本。

## 八、给你的通用原则

这次核查暴露的模式很一致：**数字都是真的，但被搬错了地方或换了名字。**

根源是你在同时维护两个项目，而简历是凭记忆汇总的。解法只有一条：

> **每个写进简历的数字，都要能当场在代码或文档里 grep 出来。**

核不出来的宁可删掉 —— 删掉只损失一行，说错了损失整份简历的可信度。

具体做法：把简历里的数字列成一张表，每个数字后面写「在哪能验」
（lab-booking 的 docs/INTERVIEW-PREP.md §四点五 就是这么做的）。
面试前过一遍这张表，就再也不会被问穿。
