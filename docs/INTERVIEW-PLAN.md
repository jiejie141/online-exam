# 第一部分：项目怎么讲

## 1.1 online-exam —— 90 秒版（背下来）

> 「这是一个**在线考试与自动判分系统**。老师出题组卷、学生在线答题、交卷后自动判分、出成绩和统计。
> 技术栈是 **Spring Boot 3 + MyBatis-Plus + MySQL + Redis + RabbitMQ + WebSocket**。
>
> 我主要解决了三个问题：
>
> **第一，判分必须准。** 我把判分写成**纯函数**，多选漏选给半分、错选零分、未作答零分。
> 写成纯函数是因为它是**唯一能被穷举单测**的形态 —— 判分算错是这类系统最不可接受的 bug。
>
> **第二，重复交卷只能生效一次。** 我**没用分布式锁**，而是靠**数据库唯一索引 + 带条件的 UPDATE**，
> 用**影响行数**判断谁赢了竞争。这样跨进程、跨机器都对。
>
> **第三，交卷不能被判分卡住。** 判分走 **RabbitMQ 异步**，消息发不出去就**降级成同步判分** ——
> 保证用户一定能交上卷。
>
> 另外卷面做了 Redis 缓存，处理了**穿透、击穿、雪崩**三个问题；
> 倒计时用 **WebSocket 按服务器时间推送**，改本地时间无效。」

## 1.2 online-exam —— 4 分钟版（在 90 秒版基础上展开）

讲法按 **背景 → 难点 → 怎么解 → 结果 → 反思** 五段：

| 段 | 内容 |
|---|---|
| 背景 | 学校/机构场景，一场考试几百人同时开考、同时交卷，判分要准、要快、要不能重复 |
| 难点 | ① 判分规则容易写错 ② 并发交卷 ③ 判分慢会阻塞交卷 |

| 反思 | 主动说局限（见 1.4） |

## 1.3 lab-booking-agent —— 90 秒版（背下来）

> 「这是一个**实验室预约与门禁系统**。用户用自然语言说『明天下午两点借光谱仪两小时』，
> Agent 解析意图、查可用时段、必要时协商备选、下单、管理员审批、门禁核验、到期自动清理。
> 技术栈是 **Python + FastAPI + LangGraph + PostgreSQL + Docker**。
>
> 最大的设计判断是：**业务规则全部写成代码，LangGraph 的七个节点只负责调模型决定用哪个工具。**
> 因为**资源冲突、资质、时长、容量这些校验必须是确定性的** —— 模型换成哪个，拦截都不能变。
>
> 第二是**幂等和多轮**：唯一索引保证时段不被重复占用；缺槽位时不是失败，而是**反问**，
> 下一轮把新信息和上一轮诉求**合并**，所以分两句话也能凑齐。
>
> 第三是**评测**：同一套用例分别跑**替身**和**真实模型**，
> **不拿替身的高分冒充模型准确率**。」

## 1.4 预判追问：8 个必问 + 答案

### Q1：你项目最大的难点是什么？

**答**（选一个，别贪多）：
> 「**判分的一致性**。判分规则本身不难，难的是保证『同一份卷子判出来的分数永远一样』，而且『重复交卷只算一次』。我的做法是把判分写成纯函数（可穷举验证），把幂等交给数据库（跨机器都成立）。」

### Q2：为什么不用分布式锁？

> 「**锁只能锁单机。** 真正的互斥应该由数据库唯一键和带条件的 UPDATE 来做 —— 它们天然跨进程、跨机器。加分布式锁是把一个数据库就能解决的问题，变成了要维护 Redis/etcd 的问题。」

### Q3：消息队列挂了怎么办？

> 「**降级**。发不出去就同步判分 —— 发不出去是基础设施问题，不是用户的问题。让他交不了卷，比让他多等 200 毫秒糟得多。」

### Q4：判分失败了怎么办？（必问）

> 「不会自动重试 —— **消费者不能把异常抛回 Broker，否则会无限重投**。
> 我做了另一件事：一个定时任务每 30 秒数一遍『已交卷但没分数』的记录，写进指标。
> **失败不会自愈，但它不再是静默的。**」

### Q5：缓存挂了怎么办？

> 「**降级直接查库**。缓存是加速用的，不是数据来源 —— 它挂掉只能让取卷慢一点，不能让学生打不开卷子。」

### Q6：WebSocket 怎么水平扩展？（大概率问）

> 「**现在做不到。** 连接存在单机内存里，多实例部署需要换成广播（Redis Pub/Sub 或消息队列），
> 而且倒计时推送那里有一处单机锁，在集群里没有意义。
> **这是已知限制，不是我不知道。**」

### Q7：为什么不让大模型自己判断规则？

> 「模型不保证每次都对。**约束校验必须是确定性的** —— 同样的输入必须给同样的结论。
> 写成代码之后，模型换成哪个都一样，拦截照常生效。
> 模型只负责『理解意图』和『决定调哪个工具』，这两件事本来就是模糊的，适合模型；
> 而『这个时段有没有被占』是确定的，不该交给模型。」

### Q8：多轮对话用户分两轮说怎么办？

> 「缺槽位不是直接失败，而是**把问题抛回给用户**；
> 下一轮把新信息和上一轮诉求**合并**（新值优先、旧值补位）。
> 所以『明天下午两点』和『用光谱仪』分两句话说也能凑齐。」

# 第二部分：技术栈知识点（答得上来）

> 按「面试官怎么问」组织。每题给一段能背的答案。

## 2.1 Java / Spring

### IoC 和 AOP 是什么？
> **IoC**：对象的创建和依赖关系交给容器管理，而不是自己 `new`。好处是解耦、可替换、便于测试。
> **AOP**：把横切关注点（日志、事务、权限）从业务代码里抽出来，用代理在方法前后织入。
> Spring 里 `@Transactional` 就是 AOP 实现的。

### Spring Boot 自动装配原理？
> `@SpringBootApplication` 包含 `@EnableAutoConfiguration`，它通过 `META-INF/spring.factories`（新版本是 `.imports`）
> 加载候选配置类，再用 `@ConditionalOnClass` 等条件注解**按需生效** —— 引入了某个依赖才装配对应功能。

### Bean 的生命周期？
> 实例化 → 属性注入 → `Aware` 接口回调 → `BeanPostProcessor` 前置 → `@PostConstruct` → 初始化方法 →
> `BeanPostProcessor` 后置（**AOP 代理在这一步生成**）→ 使用 → `@PreDestroy` → 销毁。

### `@Transactional` 什么情况下失效？
> 四个常见原因：
> ① **同类内部调用**（不走代理）② **方法不是 public** ③ **异常被自己 catch 了** ④ **抛的是受检异常**（默认只回滚 RuntimeException）。

### 循环依赖怎么解决？
> Spring 用**三级缓存**。核心是提前暴露未初始化完成的 Bean 引用（`ObjectFactory`），让 A 在还没造完时能被 B 拿到。
> **但只能解决 setter/字段注入，构造器注入的循环依赖解决不了**（那时对象还没创建）。

## 2.2 MySQL

### 为什么索引用 B+ 树？
> ① **矮胖**：一个节点存很多 key，三到四层就能支撑千万级数据，磁盘 IO 少。
> ② **叶子节点连成链表**：范围查询和排序很顺。
> ③ 相比 B 树，**数据只存在叶子节点**，非叶子节点能存更多索引项，树更矮。

### 唯一索引和普通索引的区别？
> **唯一索引**保证值不重复，插入时如果冲突会报错 —— 这正好可以拿来做**幂等**：
> 重复插入自然失败，不需要先查再插（先查再插有并发窗口）。
> 性能上唯一索引写会略慢（要检查唯一性），但代价远小于加锁。

### 事务隔离级别？MVCC 是什么？
> 四个级别：读未提交、**读已提交**、**可重复读**（MySQL 默认）、串行化。
> **MVCC** 靠**版本链 + ReadView** 实现：每行有隐藏的事务 ID，读的时候按可见性规则找到自己能看的那一版，
> **读不加锁**，所以读写不互相阻塞。

### 深分页 `LIMIT 1000000, 10` 有什么问题？
> MySQL 要**扫描并丢弃**前 100 万行，越翻越慢。
> 优化：**延迟关联**（先用覆盖索引查出主键，再回表）或**游标分页**（`WHERE id > 上次最大id LIMIT 10`）。

### 索引什么时候失效？
> ① 左模糊 `LIKE '%x'` ② 对列做函数/运算 ③ 隐式类型转换（字符串列传数字）④ 联合索引不满足最左前缀 ⑤ `OR` 连接非索引列。

## 2.3 Redis

### 缓存穿透、击穿、雪崩？
> **穿透**：查一个**不存在**的数据，每次都打库。解法：**空值也缓存**（存哨兵值，短 TTL）或布隆过滤器。
> **击穿**：**一个热点 key 过期**瞬间，大量请求同时重建。解法：**重建前抢锁**，只让一个去查库。
> **雪崩**：**一批 key 同时过期**，流量同时砸库。解法：**TTL 加随机抖动**，把过期时刻打散。

### 分布式锁为什么要用 Lua 释放？
> 因为**判断是不是自己的锁** 和 **删除锁** 必须**原子完成**。
> 如果分两步，可能在判断完之后锁刚好过期被别人抢到，然后你把别人的锁删了。

### Redis 单线程为什么快？
> ① **纯内存操作** ② **IO 多路复用**（一个线程处理大量连接）③ **避免了多线程上下文切换和锁竞争**。
> 注意：**Redis 6 之后网络 IO 是多线程的，但命令执行仍是单线程。**

### 过期策略和内存淘汰？
> **过期**：惰性删除（访问时才检查）+ 定期删除（随机抽查）。
> **内存满**：八种淘汰策略，常用 `allkeys-lru`（淘汰最久未用）和 `volatile-lru`（只在设了过期时间的 key 里淘汰）。

## 2.4 RabbitMQ

### 怎么保证消息不丢？
> 三个环节都要管：
> ① **生产者**：开启 confirm 确认 / 事务（性能差，一般用 confirm）
> ② **Broker**：队列和消息设持久化
> ③ **消费者**：手动 ACK，处理完再确认
> **注意**：这三步都做到才能说「不丢」，缺一个都不算。

### 怎么保证不重复消费？
> MQ 只能保证**至少一次**，所以消费端必须**幂等**。
> 做法：唯一键 + 唯一索引，或状态机 + 带条件的 UPDATE（`WHERE status = 'x'`），用影响行数判断是不是重复。

### 死信队列是什么？
> 消息变成死信的三种情况：**被拒绝且不重回队列**、**过期**、**队列满**。
> 死信会被路由到死信交换机，用来做**延迟任务**或**失败兜底**。

### 为什么用 MQ？
> ① **解耦** ② **异步**（交卷不用等判分）③ **削峰**（流量高峰先堆在队列里）。
> 代价是**一致性问题**（要处理重复、丢失、顺序）。

## 2.5 并发

### 线程池的核心参数？
> 核心线程数、最大线程数、**队列容量**、空闲存活时间、拒绝策略。
> 执行顺序：**核心线程 → 队列 → 最大线程 → 拒绝策略**。
> **注意队列不要用无界的** —— 无界队列会让最大线程数永远不生效。

### `synchronized` 和 `Lock` 的区别？
> `synchronized` 是 JVM 层面的，**自动释放**，不可中断，非公平；
> `Lock` 是 API 层面，**手动释放**（必须放 finally），可中断、可超时、可公平、可多个条件变量。

### CAS 是什么？有什么问题？
> **比较并交换**：只有当前值等于期望值时才更新，否则重试。底层是 CPU 的 `cmpxchg` 指令。
> 三个问题：**ABA 问题**（用版本号解决）、**自旋消耗 CPU**、**只能保证一个变量**。

## 2.6 Agent / RAG（面经重点）

### LangChain 和 LangGraph 的区别？
> **LangChain** 是链式的：一条线走到底，适合简单的「提示词 → 模型 → 解析」。
> **LangGraph** 是**图**：节点 + 边 + **条件边** + **状态**，支持**环**（循环、重试、多轮）和**人工介入**。
> 一句话：**LangChain 是管道，LangGraph 是状态机。**
> 我的项目用 LangGraph，因为需要**条件路由**（取消/审核/问答/下单四条分支）和**多轮回环**（缺槽位就反问）。

### Agent 是怎么工作的？
> 核心是 **ReAct 循环**：**思考（Reason）→ 行动（Act，调工具）→ 观察（Observation）→ 再思考**，直到能回答。
> 关键点：**工具的描述决定了模型会不会用对工具** —— 描述写得含糊，模型就乱调。

### RAG 的完整流程？
> **离线**：文档解析 → 切片 → 向量化 → 存向量库。
> **在线**：问题向量化 → 检索 Top-K → **重排** → 拼进提示词 → 模型生成带引用的答案。

### 向量检索和关键词检索各自适合什么？
> **向量**：语义相近但用词不同（「怎么退货」vs「退款流程」）。
> **关键词（BM25）**：**专有名词、型号、代码、人名** —— 这些向量容易「理解偏」，精确匹配反而准。
> 所以实战里两者**一起用**，再融合排序。

### RRF 是什么？k 怎么定的？
> **Reciprocal Rank Fusion**，倒数排名融合：`score = Σ 1/(k + rank_i)`，k 通常取 **60**。
> **k 的作用**：k 小 → 放大头部差异（更看重第一名）；k 大 → 各排名趋于平均（更稳健）。
> **诚实说法：「60 是经验值，业界普遍这么用，不是推导出来的。」** 这句比编一个理由强。

### 切片（chunk）怎么切？大小影响什么？
> 按**结构**切，不按固定字数硬切：markdown 按标题层级，word 按段落，超长表格单独处理。
> **chunk 太大**：检索精度下降（一段里混了好几个主题），还占上下文。
> **chunk 太小**：语义不完整（一句话被切断），模型答不出。
> 常见做法：**几百 token + 重叠（overlap）**，重叠是为了防止答案正好被切在边界。

### 怎么减少幻觉？
> ① **要求引用来源**，让模型只能基于检索到的内容答
> ② **检索不到就拒答**（相似度低于阈值直接说「没找到」）
> ③ **结构化输出**（强制 JSON）
> ④ **降低温度**
> **最关键的：拒答策略** —— 允许模型说「我不知道」，比强行编一个答案好。

### Tool 和 Skill 的区别？
> **Tool** 是一个**能力单元**（查天气、查数据库），有明确输入输出。
> **Skill** 是一套**完成某类任务的方法论**，可能组合多个 Tool、带流程和判断 ——
> 比如「客服 Skill」= 查订单 Tool + 查物流 Tool + 退换货规则 + 话术。
> 一句话：**Tool 是动词，Skill 是岗位。**

### 多 Agent 之间怎么协作/传信息？
> 常见三种：
> ① **共享状态**（都在同一个 state 里读写）
> ② **消息传递**（A 把结果发给 B）
> ③ **调度者模式**（一个主管 Agent 分派任务给多个执行 Agent）
> 关键难点是**上下文传递**：不能把全部历史都传给每个 Agent（太长），要**摘要 + 只传需要的字段**。

### 上下文太长怎么办？
> ① **滑动窗口**（只留最近 N 轮）② **摘要**（把早期对话压缩成一段）
> ③ **检索式记忆**（把历史存起来，需要时再检索）④ **只传结构化状态**（不传原始对话）

### 降级怎么设计？
> 「降级」要**先分清楚是哪一种**：
> - **缓存降级**（读库）：内容完全一致，只是慢
> - **模型降级**（换小模型）：内容会变，质量下降
> - **检索降级**（只走向量）：召回率下降，可能答不全
> **能拆成这三种，比背一个答案强。** 然后说明：不管哪种，**要有降级开关和监控**，不能悄悄降。

# 第六部分：最后一页纸（面试当天只看这个）

**两个 90 秒版**（online-exam / lab-booking）

**六个杀手句：**
1. 「判分写成纯函数，因为**纯函数是唯一能被穷举验证的形态**。」
2. 「幂等不靠锁，靠**唯一索引 + 带条件的 UPDATE** —— 锁只能锁单机。」
3. 「消息发不出去就**降级成同步** —— 让用户交不了卷，比让他多等 200 毫秒糟得多。」
4. 「缓存三件事：穿透存哨兵、击穿抢锁、雪崩加抖动；**Redis 挂了就降级查库**。」
5. 「**业务规则必须写成代码**，模型只负责理解意图，不参与确定型校验。」
6. 「**失败不会自愈，但它不再是静默的。**」（讲判分补偿监控）

**三句自我提醒：**
- 不确定的数字说「**大概几十条这个量级**」，别编
- 没做过的说「**了解原理，但没落地过**」
- 做不到的说「**现在做不到，但我知道该怎么改**」
